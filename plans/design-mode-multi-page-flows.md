# Multi-Page Design Flows for Design Mode

> Generated by swarm planning session on 2026-04-23

## Summary

Extend Dyad's current single-page `design` mode into a flow-aware design workspace that can:

1. Detect when the user wants to continue from an existing design and create additional pages
2. Ask which pages should be added using a Dyad-native flow review step guided by Superdesign's workflow prompt
3. Extract reusable components from the source page
4. Refactor the source page to use those components
5. Generate multiple new pages that reuse the same components and stay visually consistent

This feature should import the core Superdesign workflow into Dyad without porting Superdesign wholesale. The recommended approach is to reuse Dyad's existing design-mode agent loop, design draft persistence, and preview panel, while making `design` mode explicitly reference the workflow guidance in `D:\Project\dyad\superdesign\tmp_superdesign_app\prompy.md`. Dyad should keep its own renderer/runtime conventions, but follow the same workflow order for multi-page expansion. On top of that, we introduce a new flow-level data model and a small set of design-specific tools inspired by Superdesign:

- `plan_flow_pages`
- `read_design_draft`
- `create_draft_component`
- `read_draft_component`
- `update_draft_component`
- `execute_flow_pages`

The result is a design-mode experience where the first turn still creates one strong root page, and later turns like "设计其他页面" can expand that page into a coherent multi-page flow instead of overwriting the original draft.

## Problem Statement

Dyad's current `design` mode is intentionally scoped around one HTML draft per chat. That works for initial visual exploration, but breaks down as soon as the user wants to continue the design into a real product flow.

Today this creates three concrete problems:

1. **The design agent has no concept of "expand this design into more pages".**
   - The prompt only teaches the model to `create_design_draft` or `update_design_draft`.
   - A follow-up like "设计其他页面" is likely to overwrite the existing page instead of branching into a flow.

2. **There is no reusable component layer between source page and generated pages.**
   - Even if we generated more pages, we would have no stable mechanism to extract shared nav/header/footer/card patterns and reuse them.
   - That would produce visually inconsistent pages and make the source page drift away from the generated pages.

3. **The current storage and UI model is single-draft-centric.**
   - `design:get-draft-for-chat` returns only the latest draft for the chat.
   - The preview experience assumes one active page, not a flow of related pages plus reusable components.

### Current State in Dyad

The current implementation already gives us a strong base:

- `src/prompts/design_mode_prompt.ts`
  - supports vague-request clarification via `ask_user_question`
  - supports first draft creation via `create_design_draft`
  - supports iteration via `update_design_draft`
  - does not support flow planning or component extraction
- `src/pro/main/ipc/handlers/local_agent/tools/create_design_draft.ts`
  - creates the first draft and opens the design preview
- `src/pro/main/ipc/handlers/local_agent/tools/update_design_draft.ts`
  - replaces the current draft HTML
- `src/ipc/types/design.ts`
  - defines contracts/events for:
    - one draft record
    - ask-user-question
    - design exit
- `src/ipc/handlers/design_handlers.ts`
  - persists each draft as a JSON file under the app's internal `designs/` directory
  - provides "latest draft for this chat", but no flow/page/component relationships
- `src/components/preview_panel/DesignPanel.tsx`
  - renders one active design draft in the preview panel
  - supports inline selection and editing inside the design iframe

That means the feature is very feasible, but it needs a new abstraction level. We should not try to force multi-page generation into the existing "single latest draft" shape.

### Target Users

1. **Design-mode users** who are happy with the first page and want to extend it into related pages
2. **Product/design users** who need consistent multi-page mockups, not isolated one-off screens
3. **Implementation users** who want a stronger design handoff before switching from `design` mode to build mode

## Scope

### In Scope (MVP)

- Keep the current first-turn single-page flow as the entry point
- Add follow-up multi-page expansion in `design` mode
- Detect "expand the existing design" intent when a root draft already exists
- Present a structured page-selection approval UI like the Superdesign flow review card
- Store a root draft plus related flow pages
- Extract reusable components from the root page
- Refactor the root page to use component references before generating more pages
- Generate selected pages from the approved page plan
- Surface reusable components and generated pages in the design UI
- Keep build handoff working from the selected page or root flow context

### Out of Scope (Follow-up)

- Full freeform Superdesign whiteboard clone
- Arbitrary node graph editing between pages/components/notes
- Marketplace/import/export for component packs
- Cross-chat or cross-app reusable component libraries
- Automatic code generation from all flow pages at once
- Visual component extraction driven purely by drag selection in the canvas
- Version history per component beyond basic updates

## User Stories

1. **As a design-mode user**, I want the first request to create a single high-quality page, so that the workflow stays fast and simple for initial exploration.
2. **As a design-mode user**, I want a follow-up like "设计其他页面" to expand the existing design instead of replacing it, so that I can build a complete flow incrementally.
3. **As a design-mode user**, I want the agent to ask which pages should be added before generating them, so that I stay in control of scope.
4. **As a design-mode user**, I want Dyad to extract reusable UI pieces from the source page, so that the new pages stay visually consistent.
5. **As a design-mode user**, I want the source page itself to be refactored to use the same reusable components, so that it remains the canonical source of truth.
6. **As a design-mode user**, I want generated pages to appear as a related flow set, so that I can review and iterate page-by-page.
7. **As a build-mode user**, I want design handoff to preserve the full flow context, so that implementation starts from a consistent multi-page design system instead of one isolated page.

## PM Analysis

### Problem Statement

The current `design` mode gets users to a compelling first page, but not to a realistic product flow. That is a product gap because many design requests become useful only after the user sees adjacent pages such as details, settings, checkout, onboarding, or profile views.

Without flow expansion, Dyad's design mode feels like a one-shot mockup tool. With flow expansion, it becomes a more complete pre-build workspace.

### Proposed Scope

**MVP**

- Preserve current root-page creation path
- Add a dedicated follow-up flow path when a draft already exists
- Introduce flow planning, component extraction, source refactor, and multi-page generation
- Show pages and components in a structured design workspace

**Follow-up**

- Freeform canvas relationships and note nodes
- Richer component editing UI
- Smarter automatic page suggestions based on app type and prior chats
- Cross-flow design systems

### Success Metrics

- Users can generate a first page and then successfully add 2 or more related pages in the same chat
- Generated pages share reusable components with the source page instead of duplicating hardcoded sections
- The source page remains intact and usable after expansion
- Users can understand which pages will be generated before generation starts
- Build handoff still works from design mode after multi-page expansion

### Risks & Open Questions

- Should flow pages live under one chat only, or be discoverable app-wide?
- Should component extraction be fully automatic in MVP, or should the agent explicitly name each extracted component?
- How much of the Superdesign UI should Dyad copy versus adapt into the current preview panel?

### Recommendation

Build this as a Dyad-native extension of the current design stack, not as a partial embed of Superdesign. Reuse the current agent/tool/IPC foundations, but promote the data model from "one draft per chat" to "one flow with multiple related drafts and reusable components".

## UX Design

### User Flow

1. **Initial design**
   - User asks for a design
   - Agent clarifies if needed
   - Agent creates one root design page
   - Design panel opens on that root page

2. **Flow expansion trigger**
   - User later says something like:
     - "设计其他页面"
     - "补齐剩下的页面"
     - "继续做这个应用的其他页面"
   - Agent detects that:
     - a root draft already exists
     - the user intent is to expand, not replace

3. **Page selection / approval**
   - Agent calls `plan_flow_pages`
   - The renderer shows a structured approval card styled like the Superdesign flow review UI
   - User can:
     - accept suggested pages
     - remove pages
     - rename page titles
     - add one or more extra pages
   - Generation does not start yet

4. **Component extraction**
   - Agent reads the source page
   - Agent extracts shared UI patterns such as:
     - navigation
     - header
     - footer
     - repeated cards or list items
   - Components appear in a reusable component section styled like the reference image

5. **Source refactor**
   - Agent updates the root page so those shared sections become component references
   - The root page remains visually the same, but structurally becomes the canonical source page

6. **Flow page generation**
   - Agent calls `execute_flow_pages`
   - Dyad generates the approved pages using the extracted components
   - The generated pages appear as related pages in the workspace

7. **Review and iteration**
   - User can switch between pages
   - User can ask for edits to one page or to the shared components/system

### Key Screens/States

- **Root page only**
  - Current design panel behavior remains

- **Flow planning card**
  - Chat renders a review card showing:
    - flow name
    - page count
    - editable list of proposed pages
    - add-page action
    - cancel / generate actions
  - This should feel directionally like Figure 1, but the exact implementation can stay Dyad-native as long as the behavior follows the workflow guidance in `D:\Project\dyad\superdesign\tmp_superdesign_app\prompy.md`

- **Reusable component nodes**
  - Preview/workspace shows extracted components as reusable building blocks on the infinite canvas
  - Components should appear above the root page as separate shared nodes with names and previews

- **Generated flow pages**
  - Workspace shows the root page plus generated sibling pages on the infinite canvas
  - Generated pages should appear below the root page with clear source relationships, not as isolated drafts

- **Loading states**
  - Planning pages
  - Extracting components
  - Refactoring source page
  - Generating related pages

- **Error states**
  - No source draft exists yet
  - Approved pages empty
  - Component extraction fails
  - Source refactor fails
  - One or more flow pages fail while others succeed

### Interaction Details

- The first draft is still generated immediately when requirements are clear
- Multi-page expansion is progressive disclosure, not part of the first-turn default flow
- The page-planning step should block generation until the user approves
- Users should see that Dyad is reusing components, not just cloning HTML
- If generation partially succeeds, successful pages should remain visible and failed pages should show retry affordances

### Accessibility

- The flow-planning card must be keyboard navigable
- Page list rows must be operable without drag-only interactions
- Page and component identity must be visible in text, not color alone
- Long page titles/descriptions must truncate safely but remain available to screen readers
- Live generation states should use polite `aria-live` announcements

### Consistency Notes

- Reuse the existing `ask_user_question` interaction model rather than inventing a second approval transport
- Reuse existing Dyad chat cards for generation feedback where possible
- Reuse the current design panel shell, but extend it to support:
  - page switching
  - reusable component browsing
  - flow context

### Concerns & Suggestions

- Avoid turning this into a completely freeform whiteboard; the canvas should stay flow-structured and constrained
- Avoid fully automatic component extraction with no visibility; users should be able to understand what became reusable
- Keep "edit this page" and "edit the shared system" conceptually distinct, or users will not know why multiple pages changed

### Core Design Decisions

1. **Promote design mode from "single draft" to "flow with pages".**
   - The current draft model is too narrow for multi-page support.
   - We should add a first-class flow abstraction instead of hiding related pages inside ad hoc naming conventions.

2. **Reference Superdesign's workflow prompt in `design` mode, but keep Dyad's own interaction/runtime model.**
   - The key behavioral reference should be `D:\Project\dyad\superdesign\tmp_superdesign_app\prompy.md`, especially the branch that says a follow-up like "design other pages" should expand from the existing root draft instead of creating a second disconnected root page.
   - MVP does not need to clone Superdesign's exact `ask user question` protocol or UI schema one-for-one.
   - What matters is that Dyad follows the same workflow order:
     - detect existing root draft
     - treat follow-up page requests as flow expansion
     - plan pages first
     - extract reusable components
     - refactor the source page
     - generate sibling pages

3. **Keep Superdesign's workflow order.**
   - `plan_flow_pages`
   - `read_design_draft`
   - `create_draft_component`
   - source refactor via `update_design_draft`
   - `execute_flow_pages`
   - Skipping the source refactor step will produce drift.

4. **Refactor the source page before generating siblings.**
   - This keeps the root page as the canonical design source.
   - It also ensures future edits can target shared components instead of chasing duplicated markup.

5. **Build a constrained flow canvas, not a freeform whiteboard.**
   - Dyad should not clone all of Superdesign's whiteboard behaviors.
   - But the MVP must render root page, reusable components, and generated pages as canvas nodes with edges and source relationships.

### Data Model Changes

The main change is introducing a flow-level model.

#### Proposed Flow Model

```ts
interface DesignFlow {
  id: string;
  appId: number;
  chatId: number;
  title: string;
  rootDraftId: string;
  status: "drafting" | "planning" | "generating" | "ready" | "partial-error";
  createdAt: string;
  updatedAt: string;
}

interface DesignFlowPage {
  id: string;
  flowId: string;
  draftId: string;
  title: string;
  prompt: string | null;
  role: "root" | "generated";
  order: number;
  sourceDraftId: string | null;
  status: "ready" | "generating" | "failed";
  createdAt: string;
  updatedAt: string;
}

interface DraftComponent {
  id: string;
  flowId: string;
  draftId: string;
  name: string;
  description: string | null;
  htmlTemplate: string;
  propsJson: string;
  createdAt: string;
  updatedAt: string;
}
```

#### Storage Recommendation

Keep the current file-based storage style for MVP, but reorganize it:

- `.dyad/designs/flows/<flowId>.json`
- `.dyad/designs/drafts/<draftId>.json`
- `.dyad/designs/components/<componentId>.json`

This preserves Dyad's current lightweight design persistence approach and avoids forcing a DB migration before the flow model is proven.

#### Why Not Keep `getDraftForChat` as the Primary Model

Because the "latest draft for chat" query is not enough once we have:

- one root page
- multiple generated sibling pages
- a shared component layer

We should instead support:

- `getFlowForChat`
- `listFlowPages`
- `listDraftComponents`
- `getDraftById`

#### Workflow Prompt Alignment

For MVP, the key requirement is to align Dyad `design` mode with the multi-page workflow described in `D:\Project\dyad\superdesign\tmp_superdesign_app\prompy.md`.

That means the prompt/runtime contract should explicitly encode:

- if no design draft exists yet, generate a single root page
- if a design draft already exists and the user asks for additional pages, do not call `create_design_draft` again
- before generating sibling pages, perform page planning and reusable-component extraction
- refactor the source page to reusable components before executing multi-page generation

If implementation later proves that Dyad's current interaction payloads are too narrow for the desired review UI, we can expand renderer payloads in a follow-up. That is a UI transport detail, not the primary design decision for this document.

### Tool Design

#### `plan_flow_pages`

- Purpose:
  - propose the pages that should be added to the current flow
- Inputs:
  - `sourceDraftId`
  - `flowContext`
  - optional `deviceMode`
- Behavior:
  - prepares suggested pages
  - pauses for user approval via the flow-pages interaction card
- Output:
  - approved list of pages

#### `read_design_draft`

- Purpose:
  - fetch the source HTML when the agent needs to analyze shared patterns
- Important:
  - only needed for flow generation, draft comparison, or explicit reference
  - should not be spammed during normal iteration

#### `create_draft_component`

- Purpose:
  - turn source-page raw HTML snippets into reusable component definitions
- MVP note:
  - the component extraction target list should be small and biased toward obviously shared structures

#### `read_draft_component`

- Purpose:
  - inspect extracted component template and props before reuse or update

#### `update_draft_component`

- Purpose:
  - fix missing dynamic bindings such as:
    - `href`
    - active nav state
    - visibility
    - counters / badges

#### `execute_flow_pages`

- Purpose:
  - generate the approved sibling pages from:
    - source draft
    - flow context
    - extracted components
- Output:
  - generated page metadata in stable order

### Prompt Design Changes

The design mode prompt should gain an explicit branch like:

1. If no draft exists yet and the request is clear:
   - `create_design_draft`
2. If a draft exists and the user wants edits to the current page:
   - `update_design_draft`
3. If a draft exists and the user wants additional pages:
   - `plan_flow_pages`
   - `read_design_draft`
   - `create_draft_component`
   - `update_design_draft`
   - `execute_flow_pages`

It should also explicitly instruct:

- never call `create_design_draft` again for sibling pages
- never overwrite the source page when the user asked for additional pages
- always refactor the source page to component references before flow generation

### Rendering / Workspace Design

Recommended MVP evolution for `DesignPanel`:

- main area:
  - infinite canvas with root page centered as the source anchor
  - reusable component nodes above the root page
  - generated page nodes below the root page
  - connector lines and source labels between related nodes
- active editing:
  - only the currently selected page node uses the full editable iframe
  - non-active pages and components render as preview cards
- overlays:
  - selected element editing when in edit mode
  - component detail preview when a shared component node is selected

### Error Handling

Non-bug failures should use `DyadError` with appropriate kinds, especially for:

- no root draft exists
- no approved pages returned
- flow not found
- component not found
- source draft missing required structure
- execution cancelled by user

Partial generation failures should not collapse the whole flow. Persist successful pages and mark the flow `partial-error`.
